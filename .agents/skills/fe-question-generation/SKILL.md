# FE問題の全件生成対応

## 完了条件

依頼で指定された範囲と、[README](../../../README.md)で定義する収録範囲に含まれる、用意可能な問題をすべて生成・出題可能にする。代表例や実装しやすい問題だけを選び、残りを未対応のまま完了として扱わない。実装の難しさや作業時間だけを理由に対象から外さない。

用意可能とは、公式公開と出典を特定でき、本文・選択肢・正答・図表の利用条件と第三者著作物の扱いを確認でき、生成内容と正答を検証できることをいう。出典があるだけで利用可能と判断しない。非公開問題・漏洩資料・利用条件未確認の素材は取り込まない。現行の2025年度科目B問6の除外は、この条件の確認が完了するまで維持する。対象範囲を超える問題の一括収集や公開を、この規約から推定しない。

## 変更手順

1. 現在の配布カタログ、公式問題、生成対応一覧、利用条件の記録から対象を列挙する。固定の件数や手選びの一覧を規約上の上限にしない。収録追加時も、用意可能な対象を漏れなく含める。
2. 原問題を保持し、各原問題に、バインド前の完全な基準問題・登録済み生成器・科目に対応するミックス枠を一対一で揃える。必要な作図、本文、選択肢、正答、独自解説、出典・権利情報まで用意する。
3. 同じ入力値から本文・図・選択肢・正答・解説を一緒に生成する。知識問題も対象・条件・対応関係・問う方向を変える。選択肢の並べ替えや名前の置換だけで、答えの暗記を避ける生成対応と称さない。
4. 元の出題形式と照合する。文章を補助表へ置き換えず、元からある表・図・凡例・空欄・疑似言語・選択肢数を維持する。作図は開発側で管理する描画機能を使う。解法の補助情報や内部ノードID・接続表を出題本文へ加えない。図の代替説明は読み上げに対応させる。
5. 出題経路、バインド値、テンプレート・生成器の版、原問題・基準問題への参照、生成結果と改変の有無を保存する。年度別オリジナルでは元データと元の値を使い、生成経路では改変ありとする。再開・復習では保存した内容を使い、再生成しない。既存記録の値や正答を新しい仕様へ書き換えない。
6. 利用条件、出典表示、改変概要・詳細、独自解説の表示を確認する。問題本文・選択肢・正答・解説・図表の権利情報を一括して公式作成又はOSSライセンス対象と扱わない。

生成器はビルドに含める管理済みコードとし、問題データ由来の任意HTML・CSS・JavaScript、疑似言語、動的評価コードを実行しない。実行時AIや汎用コード実行を追加しない。

## 全件対応を維持する検証

- `scripts/source-inventory.ts` の公式公開範囲・除外理由と配布カタログを照合する。原問題と生成器を両方削除して全件対応と扱わない。年度追加時は公式の公開問数と第三者部分を再確認して範囲を更新する。
- 新規配布カタログでは `generationCoverage: "complete"` を維持する。`src/core/generation-coverage.ts` の全公式問題と有効な生成定義・ミックス枠の一対一検証を通す。検証を回避するためのフラグ削除、`partial` への変更、用意可能な原問題の削除をしない。旧データ・旧保存記録の互換処理は別に維持する。
- 問題又は生成器を変更した場合は、元の値、複数の生成値、境界値、乱数シードによる再現性、重複・不正入力、選択肢と正答の対応、本文・図・解説の整合性を確認する。計算は生成器と独立した方法でも照合し、図は原資料とレンダリングを比較する。対象追加時は全件検証の対象と期待件数も更新する。
- `npm run data:validate` と `npm run test` で配布データ・参照・登録契約・生成結果を検証する。対応範囲を変更したら `npm run doc:generation` で `docs/generation-coverage.md` を再生成する。このページを手作業で変更しない。
- Schemaを変更したときは `npm run doc:reference` でフィールド辞書を更新する。変更に応じた確認を行い、完了前に `npm run check` でテスト、本体・文書ビルドを確認する。UI説明だけの変更では問題データを再生成せず、変更を写すだけのテストを追加しない。
- ブラウザで形式を確認する場合は、適用されるブラウザ検証規約に従い、原問題と生成問題、図の凡例、文字拡大、ライト／ダーク、狭い画面を変更箇所に応じて確認する。

Schema・参照・生成テストの成功を、利用条件の充足、正答の正しさ又は全パラメータの網羅的検証の代わりにしない。確認できない外部条件は根拠と限界を記録する。

## 出典・転記・改変・ライセンスの追加規約

1. 追加・更新ごとに一次資料へ到達し、発行主体、URL、公開日又は更新日、確認日、試験区分・年度・科目・問番号・ページを記録する。過去の確認結果を別年度・別素材へ流用しない。
2. 本文・選択肢・正答・独自解説・図表を分けて確認する。第三者の引用・図表・規格文言は個別条件を調べ、不明なら配布へ入れない。GitHub同梱・ブラウザ表示・改変の用途別判断と根拠・限界をrightsへ残す。公開されているだけで自由利用と扱わない。
3. 原資料との照合で意味を維持した転記・組版だけは再録とする。誤字修正、数値変更、要約、表現の置換、独自作図への置換は内容の改変として記録し、原条件・原出典・派生参照と改変概要・詳細を継承する。類題の呼称だけで独立作成にしない。
4. 公式依存の部分へMIT／CC0を適用しない。独自解説は独自作成と表示する。出題・出典詳細・結果・復習で、question.origin.sourceRefs、isModified、changesと各attribution・rightsRefsから必要な表示へ到達できることを確認する。ライセンス一覧のリンクだけで問題単位・素材単位の表示を代替しない。
5. ライブラリ追加・更新では、採用版の配布物にある著作権表示と全条件、派生部分・フォント等の追加通知を点検する。public/notices/index.jsonへ名称、採用版、適用範囲、原資料URL、確認日、全文ファイル、hash、配布経路を記録し、原文全文を同梱する。LucideのFeather由来MITを省略しない。CDNの資産も対象とする。ビルドで実際に含まれる推移的依存の通知が不足したら配布を止める。
6. npm run data:validate及びnpm run buildで公開許可リスト・用途別条件・継承・原文通知・採用版・実バンドル依存を検査し、ライセンス一覧で範囲と全文の表示を確認する。ビルドツールだけの依存と配布コードを区別する。文書サイトそのものを配布する場合は、その成果物の依存も別途点検する。
7. 生成器の正答だけでなく全選択肢の成立条件を調べる。偶然同じ結果になる入力を含めて誤答の反例・同値性を確認する。複数正答や本文と解説の矛盾を検出したら新規出題を修正し、生成器版と基準問題改訂を上げる。知識の対応資料は意味を査読してから固定し、生成器の出力で期待値を自動更新しない。

条件変更・権利上の疑義・削除依頼は[保守方針](../../../docs/maintenance.md)に従い、新規配布・保存資源・Git履歴への影響を追跡する。取り下げ対象の本文を履歴用ファイルへ残して公開し続けない。機械検査を法的な許諾又は専門家の評価の代用にしない。

## UIでの扱い

全件対応は通常の動作と開発の完了条件として維持する。メニューへ「全問対応」「現在の対応テンプレート数」「バインド方式」「同系列の異なる入力が含まれる」などの技術的な告知欄を設けない。対応漏れを告知欄で説明して完了にしない。

年度別オリジナル／ランダムミックスの選択、科目・年度・モード・出題数・時間・開始操作は維持する。問題単位・素材単位の出典・改変・ライセンス表示と、利用条件による除外や実際の例外時の案内は維持する。メニューの技術説明を省くことと、必要な権利表示の省略を混同しない。
